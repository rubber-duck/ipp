# Shared asset ownership

`AssetManagementService` owns Host-wide resource identities, providers and consumer demand. Worlds retain typed source references; providers acquire immutable content through the separately owned [I/O service](../io/README.md). The [asset architecture](../../../../../docs/architecture/assets.md) defines the ownership and recovery contract.

Copying an asset key does not retain its resource. Unloading preserves identities retained by demand or ownership; an unreferenced idle identity may be discarded to avoid reacquisition. Final release invalidates the generation before reuse. The Host completes synchronous invalidation across all Worlds before releasing shared payloads. Embedders that progress services directly must also complete that Host lifecycle boundary, including dispatch of pending observations.

World convenience APIs for shared loaders, streams and resource observations remain available without selecting AssetDependencySystem. Only its World-local upload queue requires that System; enqueue rejects its absence with `UnsupportedDependency`, and queue inspection reports no pending work. Host-prepared sources remain observable through the ordinary World consumer fence. These APIs neither select omitted Systems nor advance simulation.

An exclusive Host lifecycle boundary has no active World phase borrows. Logical frame preparation and unfinished command batches therefore do not postpone CPU invalidation or resource destruction. The Host drains callback-strengthened release revisions before freeing payloads, and forwards resulting observations before returning. Graphics-device replacement has its own adapter boundary.

Completed outputs acquire an opaque, service-scoped publication ID over exact loaded resource keys through `retain_publication`. This keeps the existing provider, decoded data and fenced recovery source alive independently of World demand or producer ownership; `release_publication` retires only that output's consumer. `publication_resource` validates both the service and key generation. Before finishing a pending release, the Host can query `affected_publications` and invalidate their derived contributions while storage is still available. If that work strengthens the release, `finish_release` rejects the stale event and leaves the stronger request pending; the Host must drain and invalidate that request before reuse, possibly at the next safe boundary. Only ordinary orphan removal can be canceled by renewed demand; explicit unload of idle content remains destructive. Explicit `unload` of required content preserves identity for same-source recovery, while `revoke_resource` or `revoke_source_prefix` removes it after that barrier. Call prefix revocation before unregistering the corresponding external data source. Producer/session revocation uses exact resource keys; ordinary producer release and World teardown are not revocation. GPU invalidation retains decoded CPU data.

Decoded CPU availability and graphics readiness are independent. Consumers can use retained CPU data during graphics recovery; failed acquisition preserves authored references and reports failure. Immutable client sources can be prepared before component selection, and releasing producer ownership preserves recovery data still required by other consumers. Completed externally recoverable resources remain in an unused cache under a soft memory target with a non-zero [default](service.rs) that Hosts may override; 0 evicts on release. That target governs idle retention rather than admission: active demand and producer ownership may exceed it. Resource counts have no IPP quota; memory, representable identities and device capabilities bound growth.

Start with [service and demand](service.rs), [provider loading/recovery](resource.rs) and the [release barrier](lifecycle.rs). Renderer-owned loaders provide GPU representations through the same lifecycle.

[Expression definitions](formats/expression.rs) retain an immutable declaration and a shared CPU plan using the existing [IPPE format](../../expressions/EXPRESSION_FORMAT.md). Consumers own bindings, parameters and scratch, and invalidate plan access through the ordinary asset lifecycle. Resident payload accounting counts distinct shared text once within the asset; independently cloned plans may keep their allocations alive after provider unload and belong to their consumers' accounting.

The [mesh](formats/MESH_FORMAT.md), [texture](formats/TEXTURE_FORMAT.md) and [skeletal](formats/SKELETAL_FORMATS.md) format references describe the binary payloads beside their decoders.
