# World systems and Host factories

Each World exclusively owns fresh System instances; the Host retains reusable factories and shared services. Systems own subsystem behavior and bookkeeping, while components own per-instance authored and evaluated data. The [runtime architecture](../../../../../docs/architecture/runtime.md#system-composition) defines composition, borrowing and frame order.

Construction validates required and conditional predecessors, rejects invalid graphs and fixes a deterministic sequential order. Selected built-ins must match the compiled authoring contract. Initialization failure and teardown release completed instances in reverse order. Parallel evaluation, mutable System dependencies and dynamic schedules are unsupported.

The immutable World manifest admits component declarations and typed animation/constraint targets independently of the compiled schema. Creation, adoption and private restoration use the same support checks; unavailable evaluators reject authoring rather than leaving inert declarations. Core entity-link animation needs no component evaluator. Inspection of an unselected animation system returns no controllers, while its mutation APIs report `UnsupportedDependency`.

Callbacks borrow ECS data, declared predecessors and services for their phase. Typed update parameters generate bindings and dependency metadata; synchronous lifecycle callbacks remain explicit. Persistence uses the outer World boundary and System restoration hooks.

Queued commands declare foreign World lifetimes through the pure `System::command_world_references` hook. Host admission collects only borrow scope; each command, including each member of a group, receives its own restricted, short-lived [`HostIngressView`](../../host/ingress.rs) through `SystemCommandContext::host_ingress`. The owning System validates before its first mutation. The view reborrows current local storage and declared remote Worlds, root binding identities, attachment writes, input admission and publication/resource availability; it is not a generic guard or presentation grant. A source publication need not still be latest. Missing declarations, unavailable borrows and stale lifetimes fail closed, including native command scopes that did not acquire those foreign borrows. Already-admitted commands may finish while a later intent is Reserved.

Owned command payloads may carry subsystem RAII tickets for exactly-once terminal disposition and permit release. Queue filtering on session release, failed-group tails and World destruction drop those payloads without requiring another frame. Generic dispatch does not fabricate external replies after session loss; delivery and cancellation policy belong to the owning subsystem. The [command-boundary tests](../host_ingress_tests.rs) exercise these lifetimes without a GUI service.

## Lifecycle boundaries

Ordered mutations retain applied effects on failure. Every selected System invalidates affected bindings before occupied component storage or shared resource payloads can be released or reused. Asynchronous subscription delivery cannot hold this barrier.

Update-requested removals wait until all scheduled updates return. Later Systems still see the target during that phase; guarded identities prevent removal of replacements. Lifecycle/finish callbacks cannot extend the removal queue. Shared asset release additionally waits for all prepared World updates to finish. Prepared render/query outputs must reflect completed cleanup before publication.

## Source entrypoints

- [System and factory contracts](composition/system_trait.rs), [validated schedules](composition/schedule.rs), the [World manifest](composition/manifest.rs), the [compiled catalog](composition/catalog.rs) and [scoped contexts](composition/contexts.rs) define extension boundaries.
- [Typed update parameters](composition/parameters.rs) and [parameter examples/tests](../../../tests/system_parameters.rs) show declaration and borrowing mechanics.
- [Ordered mutation](../mutation/mod.rs), [deferred removals](../removals.rs) and [asset lifecycle](../../services/asset_management/lifecycle.rs) implement invalidation and publication boundaries.
- [Persistence hooks](composition/persistence.rs) let each System capture and restore its own contribution through the [serialization service](../../services/world_serialization/README.md).

A System stores one `SystemBindings<Self>` field. Its factory uses `SystemBindings::resolve(context)` and `SystemBoundUpdate::dependencies()`. Inside its ordinary `impl System`, `ipp_core::system_update!(bindings)` supplies the dynamic update adapter. Lifecycle, command and persistence callbacks remain explicit methods on the same concrete instance. [RenderSystem](render/system.rs) consumes optional rig diagnostics and immutable assets; [AssetDependencySystem](asset_dependencies/system.rs) borrows Animation plus mutable asset service access. They share this generated mechanism with extension Systems in [system_parameters.rs](../../../tests/system_parameters.rs).

Bindings are private typed slots scoped to the constructing World and dependent System. Resolution checks declared edges and concrete types once during initialization. Update lookup directly checks the stored identity and slot; there is no per-frame dependency collection, graph traversal, redundant allow-list scan or cloned System state. Parameter structs and service slots live on the stack. Each service slot can be consumed once per callback, allowing distinct mutable Services simultaneously; duplicate service parameters reject construction. Only Services implement mutable parameter access. The added `syn` parser features belong to the host-side proc-macro crate and add no runtime dependency.

`SystemUpdateContext::inputs()` splits ECS, immutable declared System reads and independent service borrows. Systems that need synchronous evaluated writes can instead use the outer `SystemRuntimeAccess`; all temporary input borrows must end before lifecycle dispatch reborrows Systems mutably. The current instance is supplied separately and remains visible to every invalidation callback. The low-level dependency APIs remain available for construction, teardown and specialized callbacks. Cross-World, cross-Host and cross-dependent bindings are rejected.

Scoped `SystemEcsAccess`, `SystemRuntimeAccess` and `SystemWorldView` observations (`inspect_effective` and `SystemWorldView::entities_effective`) return the same `EntitySnapshot` as outer inspection: identity, metadata, link and stored components. There is no separate authored or effective view. Persistence uses the outer `WorldContext` boundary and its generic restoration hooks. Reading ECS data does not borrow other Systems or retain an extra component mirror.

## Lifecycle and frame boundaries

The [frame loop](../update.rs) and [ordered mutation](../mutation/mod.rs) dispatch generic frame, batch and operation hooks. Systems interpret their own commands, reconcile their own changes and detach their own report events. Constraint owns declaration binding and scalar evaluation, Animation owns playback commands and sampling, and Camera/Geometry own their queries. A final `System::observe_frame` pass after every System's finish pass lets the lifecycle publisher compare watched fields with the values it last reported. No component mirror is retained.

Earlier operations of a failed batch stay applied; an invalid operation has no effect. Generic commit calls every System's validation and synchronous `before_commit` hooks while old occupied storage remains live. Cleanup restores are owned values queued into the same barrier; if cleanup changes another component, every handler sees that change before any storage is cleared. Only after all handlers finish may storage be released, allocator slots reused, prepared values installed and applied observations published. `after_commit` refreshes subsystem bookkeeping. Evaluated commits do not publish client-authored component events. `SystemWorldView::effective_component` can inspect old storage even when deletion has been staged.

Explicit update-originated removals use `SystemEcsAccess::defer_remove_entity` or `defer_remove_component` (also available on `SystemRuntimeAccess`). [removals.rs](../removals.rs) stores only generational identities and component incarnations, deduplicates requests, bounds them by `WorldLimits::max_operations`, and drains in request order after every scheduled update has returned. Later Systems still see queued targets. Stale requests cannot delete replacements. Lifecycle and finish callbacks reject new requests, so cleanup cannot create an unbounded cascade. Ingress removal and same-batch recreation keep their existing ordered semantics. Render callbacks mark prepared output dirty and rebuild before report extraction; asset release clears prepared rows before they could retain a released source.

The prepare-evaluation pass initializes internal component inputs before Animation samples them; scheduled evaluation produces final component results. Skeleton owns its component's local/global pose allocation, Skin owns its palette, and bounding/picking components own evaluated geometry. [Hierarchy and terminal LookAt](hierarchy/README.md) keep affine placement and aimed rotation in their components, with distinct initial, terminal and final propagation passes. Systems own algorithms and shared bookkeeping. Invalid numerical rig results retain their allocation but suppress consumption until valid again. Typed internal animation targets bypass the public schema while public fields remain ordinary authored inputs.

## Shared assets and persistence

The resource service queues destructive releases. Host forwards transitions to every World and System, waits until all prepared World updates finish, completes every pre-release callback and component cleanup barrier, then releases payloads or identities. A single completed World cannot authorize a shared release while peer updates remain prepared. Payload unload preserves resource identity and indexed animation clocks/binding descriptions; actual identity/source invalidation follows whole-controller invalidation policy. The [asset service](../../services/asset_management/README.md) documents residency and demand bookkeeping.

LifecyclePublisher owns subscription filters and bounded per-session queues. Systems receive synchronous callbacks independently of subscription state. Publisher records owned applied entity/component/asset observations, and transport drains them asynchronously; slow clients cannot retain component or resource borrows.

Every System has save/load callbacks with empty defaults. Generic World capture supplies selected identities, stored components and shared byte accounting; restore supplies fresh identity maps after generic component installation. The [serialization service](../../services/world_serialization/README.md) owns the current container format and opaque named contributions; no legacy adapter is retained. Animation owns its codec, reference validation, clock capture and driver reconstruction. Evaluated component buffers are never serialized, and unknown/unselected contributions reject restore explicitly.

[Host/system tests](../../../tests/host_systems.rs), [parameter tests](../../../tests/system_parameters.rs), [asset barrier tests](../../../tests/system_asset_lifecycle.rs) and internal storage tests cover generic contracts on real Host-owned Worlds. Maintained native WebSocket/browser worker suites cover lifecycle, animation, geometry and snapshots through generated clients; WebGL and GLES captures verify evaluated output and recovery. Parallel execution, mutable World-system dependencies and dynamic schedules remain outside this implementation.

## Compiled numeric evaluation

Per-frame evaluators use [typed component bindings](../direct_bindings/component_binding.rs) and [retained component queries](../direct_bindings/component_query.rs). Bindings originate from stable storage cells, not temporary mutable references; their lifecycle owner discards them before incarnation destruction. Access borrows the owning World's storage for each read or write. These helpers allocate only when membership/capacity changes and add no per-element virtual dispatch. Query owners call their before/after commit methods; preparation covers initial construction and restoration once.

`System::before_numeric_update` is the batched derived-result notification for compiled numeric writes. Its context exposes affected keys and old values, with no structural cleanup API. Numeric updates do not call commit validators or manufacture component replacements. Systems retain structural hooks for client edits, discrete resource/relationship changes and storage lifetime barriers. Output-dependent arithmetic guards are separate from binding/type validation.
