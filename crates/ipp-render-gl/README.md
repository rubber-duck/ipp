# Shared GL renderer

`ipp-render-gl` provides shared WebGL 2 and GLES 3 rendering through a compile-time device boundary. Rust consumes completed immutable World publications; platform Hosts own contexts, surfaces, clocks and presentation. Rendering never advances simulation. The crate depends only on `ipp-core` and always compiles every capability's presentation path, including Surfaces, GUI, deformation, shadows and particles; a World's System selection decides which of them run, and their programs, targets and buffers are created on first use. Every draw returns a frame summary, and every build keeps render statistics, Surface cache records and custom-material fallback reasons; the `instrumentation` feature adds testing overrides of renderer-owned budgets. The [rendering architecture](../../docs/architecture/rendering.md) owns system boundaries and color conventions.

## Resources and recovery

Install RenderService loaders before creating resources. Host service progression decodes and uploads meshes and compiles requested programs before reporting graphics readiness. Presentation consumes ready resources and declares further demand. Missing required resources skip affected draws; custom materials follow their defined fallback chain.

GPU readiness and CPU availability have separate lifetimes. Graphics failure/recovery preserves usable CPU data and resource identities. Shared release completes the Host's all-World invalidation barrier before reuse. [Graphics loaders](src/services/render/assets.rs) and [RenderService](src/services/render/service/mod.rs) implement these boundaries.

A usable, explicitly selected Camera or Canvas publication is required for draws. `RenderService::prepare(&mut HostRuntime, Option<(OutputRef, WorldPublicationId)>)` declares private program demand for exactly that current root and its completed nested Camera/Canvas outputs, separately from `draw(&HostRuntime, OutputRef, WorldPublicationId, WorldViewport, presentation_time)`. Other root selections do not contribute recipes or receive this renderer's demand. Public drawing requires the Host's current root selection, publication and exact viewport, including device pixel ratio; it never selects or resizes a view. Historical output lookup does not authorize presentation, and nested draws require completed attachment authority. The Host progresses resources; drawing never borrows a World or resolves an authored source name. Missing or invalid camera data clears the target and permits later correction, while mismatched viewports fail before GPU work. Camera and shadow culling use published conservative geometry in the containing affine domain; missing or unproven enclosures preserve visibility.

Preparation binds one Host catalog at a time. Explicit `prepare(old_host, None)` retires selection-specific demand/caches and releases this binding, including after the selected World has been destroyed; call it before dropping a Host if reusing its renderer. Unavailable selection retires stale demand/caches but does not authorize switching catalogs. Preparation, drawing, `unload_host` and device replacement reject a different Host with `RenderError::HostCatalogMismatch` before changing either catalog or selected caches. One bounded record stores this lifetime, not a map of departed Hosts. Demand withdrawal fences exact World and resource identities and never replaces another World's authored/source ownership or bypasses the Host release barrier. Graphics release uses the fallible `unload_host(&mut HostRuntime)` boundary, not a World-only unload. Recovery preserves the catalog binding and reuses the selected publication's CPU leases; it is not deselection.

Spatial attachments share one depth, lighting, shadow and transparent-ordering domain with World-qualified identities. Preparation, drawing and publication picking share the Host's output-aware spatial traversal: unscoped edges and edges owned by the exact containing Camera remain eligible, while other owners are excluded. Raw publication availability alone grants no presentation authority. SurfaceCamera outputs prepare child-first into independent linear-color/depth targets; only root presentation performs display conversion. Exact publication leases supply shader definitions, textures, mesh metadata and other source data, while palettes and material values remain borrowed from owned publication chunks.

Canvas presentation consumes producer-owned ordered primitives and exact attachment slots. Retained box, glyph and analytic streams are keyed by the exact Canvas output; root DPR and nested Surface density/clip mappings stay distinct. Canvas-owned attachments do not leak into unrelated outputs. Direct Canvas painting composes inside Camera views and nested Canvas slots, including child-first Camera targets; shape and glyph device support does not require GUI controls. Nested Canvas drawing uses an explicit stack. Inherited opacity applies per primitive; Camera images are single primitives. Optional whole-Surface caches bake inherited opacity into the raster and composite without a second attenuation. Cache dependencies include nested output lifetimes, availability, resources and raster generations, even when parent paint storage is unchanged. Composed-input routing is not yet connected to this consumer.

Debug publications retain all derived parts with individual visibility and optional explicit color. The current containing Camera resolves show-all and default color, including for frozen spatial children; prepared-part counts are not visible-draw counts. `forget_world` immediately releases that World's nested Camera targets independently of later preparation.

Render preparation reuses evaluated geometry, packs selected lights once per submission and retains scratch buffers for sequential World draws. Material ordering groups opaque draws by shader and values while preserving the existing transparent depth order. Devices cache current GL bindings and exact per-program uniform values within a submission, invalidating them at frame entry, resource deletion and context recovery. These choices affect draw preparation and redundant uploads without merging ordinary draws. The [renderer source](src/services/render/service/) owns the implementation.

## Output inclusion

The Host's [presentation coordinator](../ipp-host-session/src/services/presentation.rs) admits `afterOutputs` beside the existing sequence and exact-root-publication fences. It resolves and deduplicates exact output tokens, then freezes each World's next evaluation tick before the Host's ordinary evaluation/draw phase. Callers await their authoring or action ACK before requesting this cut. Idle and callback-only actions need a completed evaluation, not a changed paint revision. Unavailable outputs never authorize an extra evaluation; pending work retains the ordinary timeout, cancellation and connection lifetime. Root/context/selection fences still apply.

`HostServices::present` receives a borrowed `PresentationCompletion` with capture storage and requested `OutputPublicationObservation` slots. `RenderService::draw_observed` fills only outputs actually composited into the successful selected draw. Offscreen Camera preparation is not inclusion until its image is consumed. Direct Canvas scopes propagate stale nested-image state to their containing output without suppressing unrelated included siblings. No World storage is borrowed during drawing.

Whole-Surface images retain their painted content stamp and exact participating output identities with the existing cache entry. Equality with the current content stamp allows an unchanged image to witness a later completed publication without repaint. Changed dependencies or a stale image baked into a containing cache prevent that equivalence until an ordinary successful repaint. This receipt is image-lifetime metadata, not publication history or a permanent observer registry; it does not change refresh policy. Requested source publications are collected only for the current draw, and ordinary reuse without observers or a containing image collector does not traverse extra output graphs.

The protocol bounds both lists by the existing maximum message bytes, with space for the larger reply. Ingress charges decoded request storage; the connection's existing reliable-output reservation covers pending cut/source metadata, then transfers to the encoded reply and actual transport completion lease. Capture reservations remain distinct. No queue or byte budget is increased. An observation reports source identity and evaluation tick, not independent measurement of total allocator/GPU memory.

The maintained `output-inclusion` suite exercises generated native WebSocket/GLES and development/minified worker/WASM/WebGL clients, callback-only and idle cuts, logical gating, cancellation, lifetime replacement and retained-image pixels. Those captures are correctness evidence outside benchmark timing. Native Host and failure-injecting renderer tests additionally establish the exact next-draw cut and cache refresh boundary; they are not real GPU timing evidence. Use the [regression entry point](../../docs/development/building.md#regression-entry-point) with that suite and `presentation`/`surface-cache` selections.

## Native host binding and smoke fixture

A RenderService currently supports one graphics context and synchronous submissions across multiple Worlds. Simultaneous independent contexts over one catalog are unsupported. Native embedders supply context lifetime/currentness and loaded entry points; the renderer creates no window or event loop.

The [native smoke guide](examples/smoke/README.md) owns EGL setup, fixture commands and capture instructions. Browser distributions use the maintained [assembler](../../packages/ipp-client/tools/assemble.mjs) with the client generated from that WASM artifact's own contract; the [browser render host](../../packages/ipp-client/src/render-worker.ts) owns setup and recovery.

The `render-publications` suite checks renderer algorithms, root authority, immediate target retirement, affected caller compilation and WASM compilation. `check:gles-publications` uses the maintained EGL driver with completed-frame image assertions for moved-parent placement, containing debug policy, device replacement, merged transparency, cross-World shadows and nested Camera color/depth. Two distinct roots verify selected-only program demand, isolation from an unselected unsupported shader, warm reuse, switching, independent source ownership, deselection and recovery. Its captures also exercise raw Canvas root DPR/Y-down placement, nested Canvas density and clips, painter order, retained zero-upload frames and Camera–Canvas–Camera composition. Opacity/overlap captures compare direct and cached composition; converted font/drawing/bitmap captures exercise retained glyphs and exact leases through source edits. The native bounded-stack test covers 1024 nested Canvas Worlds; it is not WASM execution evidence. Run these selections through `python tools/ipp.py regression --suite render-publications --only check:gles-publications` with `IPP_EGL_LIBRARY_DIR` configured. This direct-core/GLES evidence is not browser or transport coverage. GUI controls, composed-input receipts and platform adapters migrate at their coordinated interface checkpoints.

## Runtime shader templates

[Shader composition](src/services/render/shader.rs) uses templates whose snippets immutable recipes select at runtime. Material values remain uniforms. [Program providers](src/services/render/program_assets.rs) compile through ordinary resource progression/recovery. The [custom material guide](src/services/render/CUSTOM_MATERIALS.md) owns the GLSL authoring interface, fallback, transparency and instancing contracts.

## Direct lighting and spotlight shadows

Standard rendering includes unlit/PBR materials, textures, custom materials and geometry visualization. Direct lights and uniform ambient fill are supported; optional spotlight shadows fall back to unshadowed illumination when capacity is unavailable. Image-based lighting, MSAA, automatic LOD selection and general residency scheduling remain unimplemented.

The maintained `lighting`, `custom-materials`, `geometry` and particle suites retain completed-frame evidence and recovery artifacts. Native smoke proves actual GLES rendering; browser/native integration suites add generated-client and transport coverage. Build success alone is not rendering evidence.
