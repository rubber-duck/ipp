# GUI and Canvas Systems

[Architecture overview](../architecture.md) · [Runtime strategy](../plans/runtime-and-rendering.md#gui-implementation-approach) · [React strategy](../plans/react-reconciler.md#gui-declarations) · [Persistence strategy](../plans/ecs-serialization.md#gui-state)

## Ownership and scope

React and ordinary generated clients declare interface entities and application behavior. Selected GUI Systems own headless layout, interaction and immediate feedback and apply user actions to control fields; platform adapters supply native input services. GUI evaluates into retained [Canvas output](rendering.md#surface-presentation), without a React round trip or a second renderer.

Layouts, controls, styles and raw text/drawing/bitmap leaves are ordinary entities/components using the core ordered tree. In a World that selects the Canvas System they are content of [the World's one canvas](rendering.md#surface-presentation); a panel needing its own scope is its own World. A World may select GUI alongside other capabilities; there is no separate GUI World type or node-authoring protocol. A parent entity's Surface attachment presents exactly one child World: its canvas, or an explicit camera output. Surface dimensions and placement belong to the parent; the canvas's density and content belong to the child. Systems produce derived paint rather than issuing client commands to rewrite authored content.

V1 supports in-world panels, mouse/keyboard/touch, layout containers, text/drawing/image leaves, buttons with a selected state, checkboxes, sliders (horizontal, vertical, dial and two-thumb range), single-line text inputs with optional masking or a number, colour controls, scroll views and virtual lists, item groups, and overlays confined to their canvas. Tabs, trees, menus, dropdowns, popovers, tooltips, dialogs, toasts and similar composites are client compositions of these in the [React kit](#client-and-persistence-boundaries). It includes semantic metadata, but no screen-reader bridge. CSS compatibility, arbitrary constraint solvers, screen-space windowing or overlays that leave their canvas, XR, simultaneous independent viewers, rich/multiline editing, complex shaping/bidi/emoji, arbitrary in-plane clip transforms, automatic momentum in generic ScrollView/VirtualList controls, multi-finger gestures and touch long-press are outside this scope. Client-composed pane navigation may opt into the AnimationSystem’s spring and decay playback; the application chooses its selection and snap policy while core retains input routing and animation ownership.

## Identity and authoritative state

GUI targets use ordinary World-scoped generational entity identities and exact component incarnations. Reordering or reskinning preserves entity identity; removal, replacement and teardown invalidate property access, animation, interaction and pending work before reuse. Compact skin parts retain stable part identities independent of generated primitives. Layout consumes the core tree; delayed callbacks for momentary effects retain the logical ancestry recorded for their effect rather than reading a later tree.

Configuration, styling and control state use ordinary component fields and ordinary animation. Compact theme and part tables may use compiled rows, but entity structure and control identity do not live in parallel node tables. Committed values and scroll position, geometry and range are fields of the control component, as are a button's selection and, through its visible field, an overlay's open state; inherited eligibility is on GuiBehavior and evaluated bounds on the system-written CanvasBounds. Every control therefore requires GuiBehavior and CanvasBounds, so a World authors controls only when it selects Canvas beside GUI. CanvasStyle is an optional override of placement, layer, tint, opacity and clip; controls do not require it, and explicit client skins supply their appearance. Focus, pointer interaction, a group's active item, an overlay's recorded invoker, pending delays and repeats, native text composition and the presentation preferences are GUI System state; focus, pointer interaction, active items and the preferences are read through System queries. Layout, paint, hit regions and publications are reconstructible outputs. Numeric animation retains prepared access with lifecycle invalidation.

A control's value is an ordinary field that clients may write directly or change with compare-and-set; clients observe it by field subscription. The runtime writes the same fields when input changes a value, selects a group item, or opens or closes an overlay. Actions express user intent: relative operations, semantic value changes and focus, validated against entity/component identity and eligibility. Presses, submissions, rejected or discarded numeric entries and context requests are momentary effects. Runtime defaults are declared before input dispatch. Application callbacks observe committed changes and cannot retroactively cancel them.

Removing a GUI subtree explicitly removes its descendant entities through core lifecycle operations. Ordinary parent deletion retains the core non-owning behavior; React teardown deletes only the entities and components it created or adopted and cannot remove other children by implication.

## Layout and presentation

Constraint layout shares the [Canvas content convention](rendering.md#surface-presentation): a top-left origin, +X right and +Y down. Authored lengths are logical units. Each top-level entity and each [overlay](#controls-and-composites) is a layout root within the canvas extent. The canvas's units-per-metre density, [Canvas System state](rendering.md#surface-presentation), maps content to Surface metres and changes layout constraints without a GUI-specific axis flip. Output/view context supplies the canvas extent; Surface owns placement into parent space independently of camera motion. Layout components compose min/max constraints, flex and text measurement without an iterative cross-node solver or a Transform requirement on every GUI entity.

Flow containers own spacing between participating children and their default cross-axis alignment; an explicit child alignment takes precedence. These are neutral layout inputs. The client kit supplies skin-scaled spacing, padded content and consistent control sizing, while connected surfaces can explicitly use an edge-to-edge composition.

Animation precedes layout. Layout properties cause reflow; visual translation/scale move paint and hit regions together. Retained output changes only with relevant inputs. Camera-only changes update projection and placement without remeasuring text or reflowing the tree.

Paint and hit testing share evaluated layout, visual transforms, [layers](rendering.md#surface-presentation) and intersected rectangular clips. GUI prepares ordered parameterized shapes, glyphs, complex drawings and bitmaps through the shared Surface preparation boundary. Ordinary controls prefer [parameterized boxes and retained presentation](rendering.md#gui-shapes-and-retained-presentation); RenderService owns coverage, GPU packing, glyph reuse and compatible contiguous batching under ordinary scene depth, transparency and colour rules. Layout supplies shape dimensions independently of corner and border dimensions. Decorative glow affects paint bounds only; it does not create a larger hit target. Missing resources affect their dependent work, and normal asset readiness/recovery rebuilds it.

A VirtualList is a ScrollView whose content extent derives from an authored item count and per-item extent estimate rather than from present children; a declared child's measured extent replaces the estimate while it is declared. The runtime owns its scroll math, clips and scroll bars, anchors the committed offset so measurements never move visible content, and writes the wanted item range to the control's fields when offset, viewport or measurements change. Explicit item-index components determine child placement independently of realization order; scroll-to-index uses the same model. Missing items never delay scrolling.

When content or item count shrinks, scrolling retains the clamped position and surviving visible anchor. Later growth never resurrects discarded out-of-range intent. Measurement changes preserve the visible anchor within the remaining scroll capacity; layout normalizes the stored position before publishing matching paint, without waiting for geometry to stop changing. Realized items remain ordinary entities in the containing Canvas World, not separate Worlds; the client declares and deletes them.

[Optional Surface texture caching](rendering.md#optional-surface-texture-caching) operates on evaluated paint under the rendering quality policy. It does not throttle GUI evaluation or input; focus and active interaction select current direct presentation so controls do not remain visually delayed by a distant cache's refresh cadence.

## Controls and composites

The slider is the one scalar control, presented horizontally, vertically or as a dial. It may fill from an origin value rather than its minimum, and may hold a second ordered value as a range: drags stop at the other thumb, and both values change in one write, which is refused if it would invert them. A dial drags relatively along the vertical axis and never jumps to the pointer. A text input may hold a number: the committed number, with its range, step and display precision, is distinct from the text being edited, which commits on Enter or blur clamped to the range, leaves the number unchanged when it does not parse, and is discarded by Escape. Up and Down step it, and its decrement and increment parts step it on press and repeat while held. The colour control holds one HSVA value in sRGB encoding and paints its saturation-value field, hue rail, optional alpha rail and swatch from it in the same frame. A range's thumbs and a colour control's surfaces are focus stops within their control: its focus names the part, which takes the focus ring, its own pointer feedback and its own arrow keys. Formatted readouts, scales, hex and channel entry and presets are client composition.

A Button is the item control of composite rows, tabs, options, menu commands and toast bodies, and a checkbox of rows that toggle. Its selected field paints through the checked part variants, which also give an invoker its open look. GuiBehavior can mark a control as not focusable: it is not a Tab stop, and pressing it leaves focus where it is, so pressing an option, a remove mark or a toast keeps focus on the trigger or field. Entities that are not controls stay inert, except that an open light or modal overlay takes the pointer from what lies beneath it; a composite part that needs hover, press or a hit that blocks what lies beneath is a Button.

A GuiGroup makes the controls below it, down to any nested group or item, its items in tree order; controls inside an item, such as a close mark on a tab, are part of it. Arrow keys along its axis, Home and End move among its eligible items and stop at the ends. When the items take focus, the group is one Tab stop entered at its selected item, or its first, and arrows move focus: tabs, tree rows, radio and segmented options. When they do not, the group has an active item instead, which paints as hovered while focus stays on the trigger or field: pointer hover moves it, and while its overlay is the topmost open light or modal one in the focused control's canvas, arrows move it and Enter, or Space when the focused control is not a text input, activates it before the focused control: menus, option lists and suggestions. A group may keep one item selected: activating an item selects it and clears the others, and optionally arrow movement selects too. Selection stays in the items' selected fields, which clients may also write.

An overlay is an entity with a GuiOverlay that establishes an ordering and clipping scope above ordinary [component layers](rendering.md#surface-presentation). The canvas orders four semantic bands: content, popups, dialogs and notifications. Authored content layer offsets cannot outrank an overlay band. Overlay interaction mode is independent of its priority band. Each overlay's ordinary descendants resolve relative component layers within its scope; a nested popup stays above its owning overlay and inherits at least its owner's band. Same-band sibling overlays follow core tree order as complete scopes, so a later dialog stays above an earlier dialog and its nested menus. Notifications retain their higher band. Opening an overlay restarts inherited clipping at the canvas extent, while its own descendant clips apply; ordinary raised components remain clipped by their ancestors.

An overlay leaves its parent's layout flow, is laid out as its own root and is placed against its parent's evaluated box, or the canvas when it is top-level, at an authored side and alignment and offset by its own translation; it flips to the opposite side when that side lacks room and the opposite one has more, shifts to stay inside the canvas and is limited to the room available, so its content scrolls. It is open while visible; clients write that field, and the runtime writes it as the overlay's mode decides. A closed overlay has no layout, paint, hits or traversal. A manual overlay, such as a toast stack, changes only by client writes. A light overlay, such as a menu, option list or popover, takes the pointer from what lies beneath its box; it closes on a press anywhere outside itself and its parent's subtree, which is then swallowed, and when focus leaves both. A press closes the open light overlays of each canvas from the topmost down to the first it lands in, stopping at a modal one, so a press on a trigger reaches the trigger. A modal overlay, such as a dialog, blocks pointer, hover, wheel and keyboard input to what lies beneath it in its canvas and keeps Tab within itself, while other panels and the scene stay usable. A hint, such as a tooltip, opens after a delay while its parent is hovered or holds visible focus and closes after a short grace when that ends, at once when its parent is pressed, and on Escape; it is inert to the pointer, takes no focus, and one is open per canvas. When a light or modal overlay holding focusable controls opens, the runtime records the focused control as its invoker and moves focus to the overlay's first focusable control in the current focus-visible modality; closing the overlay returns focus to the invoker if focus was inside and the invoker is still eligible. The wheel's scroll chain ends at an overlay. Delays, grace periods and held repeats advance with the Host clock, never a client timer.

## Evaluation and input

GUI separates local mutation/control and layout through declared System dependencies, with input routing at the composed-view boundary. [The runtime schedule](runtime.md#frame-order) owns parent/child frame order; local selected passes remain fixed. AnimationSystem remains the sole sampler, including skin transitions.

Input arrives through ordered, session-fenced ingress for a presented root. Routing transforms rays/coordinates through spatial and Surface attachments against completed layout and camera/geometry publications, then queues ordered actions for the target World's next mutation boundary before animation. It does not mutate control values, reflow between events or recursively evaluate Worlds. Pending focus/capture/gesture decisions preserve input order. Actions revalidate the attachment path, entity/component incarnation and context; effects identify their source presentation/publication and target World effect tick.

Inherited eligibility, pointer interaction scope and focus scopes extend to the whole canvas and end at its World boundary. One active input context per presented root coordinates panels, focus and pointer identities across attached Worlds. Other clients may author or observe without acquiring input ownership. Uncaptured input selects the nearest eligible front-facing panel along the composed view path and, within it, the eligible entity first in reverse [layer and painter order](rendering.md#surface-presentation) within clips. Explicitly marked picking geometry blocks input; visual occlusion alone does not. Comparisons use the containing view's distances and deterministic World/entity ties. Unavailable frozen output retains its occlusion without click-through. Captured input retains its target only while its full attachment path remains live; input for a removed capture target is reported unavailable. Unhandled input is observable for scene controls without duplicate dispatch. A panel is opaque to the scene: a press of any button on panel content, including any layer surface of an [exploded](rendering.md#surface-presentation) panel, that selects no eligible control is blocked, while an unconsumed wheel still reaches the scene. A secondary press on a control, and the Menu key or Shift+F10 on a focused one, are context requests: they focus the target as a press does and publish a momentary context effect naming it and its canvas point, from which the client opens a menu.

Runtime interaction owns hover, press/cancel, capture, focus scopes, groups, overlays and keyboard traversal across attached Worlds, which follows tree order regardless of layers. With no focus, Tab and BackTab enter the nearest eligible panel by view distance at its first or last control; traversal continues across panels, with back-facing panels ordered after front-facing ones. Logical focus is the keyboard target of the input context presenting its World, however it was set: a `GuiAction` focus moves that context's target and blurs its previous one, so the next key reaches the newly focused control. Focusing a control, or moving a group's active item with a key, scrolls its scroll-view ancestors by the least amount that shows it. Enter or Space presses a focused button and Space toggles a focused checkbox; arrows move a focused value control by its step and, with Shift, by its fine step. The wheel adjusts the eligible slider or dial under the pointer without changing keyboard focus, choosing the pointed range thumb; numeric text inputs and colour rails still require focus, and elsewhere the wheel scrolls. Escape discards an uncommitted numeric edit; otherwise it closes the topmost open overlay that is not manual in the focused control's canvas, or with nothing focused a hovered control's; otherwise it blurs focus. Touch arbitration resolves tap versus slider/scroll drag and cancels the losing press; nested scrolling passes unused movement outward, and unconsumed movement is reported unhandled. Platform adapters convert wheel input to Canvas logical units before routing: the browser adapter counts wheel notches (100 CSS pixels, 3 lines or an eighth page each) and scrolls a configurable step per notch, a quarter logical unit by default. Hiding, disabling or removing a control, losing platform focus, detaching its path, and releasing/replacing an input context cancel affected interactions. The focus ring is focus-visible: keyboard and programmatic focus paint it, while pointer-press focus omits it except on text inputs. Session teardown fences queued work before identities can be reused.

## Text and skins

Text measurement and rendering share immutable font metrics and original glyph identities. Preserve Unicode source text and edit at grapheme boundaries, while rendering guarantees remain basic LTR Latin. Wrapping, glyph placement, caret and selection geometry use the same headless metrics. The runtime owns text width calculation for proportional and fixed-width fonts. Clients declare content sizing and constraints; client presentation decisions that need measured dimensions consume evaluated results rather than estimating glyph advances. Runtime and browser text offsets require explicit conversion against the text they index.

A masked input presents one mask glyph per grapheme, including provisional composition, while committed and provisional text and native editing offsets retain the actual Unicode text. Reveal changes presentation on the same control without replacing its value, selection or composition; placeholders remain readable. This is a presentation capability, not an authentication or secret-storage boundary.

Committed text is distinct from provisional composition. Single-line inputs publish a momentary submission effect outside composition. The platform adapter owns native focus, clipboard, IME, candidate placement and trusted-gesture soft-keyboard access; its temporary native buffer synchronizes through target- and focus-generation-fenced edits. An external change of the committed text invalidates delayed selection/composition and refreshes native state. Platform failure does not transfer text authority to the DOM or imply a successful edit.

Core owns control semantics, layout evaluation, text editing, value-to-part geometry, input, focus, state resolution and Host-clock animation. It exposes generic typed part, measurement and motion inputs without shipping a palette, named look catalog or aesthetic timing preset. Skin-owned dimensions resolve through ordinary theme data and per-control overrides; measurement, painting and hit testing consume the same geometry. Generic text/layout rules, scalar constraints and mathematically valid field defaults remain runtime behavior.

A skin is a client-owned collection of shared theme definitions, measurement settings, motion rows, composite tokens and optional immutable drawing, font, bitmap and shader assets. Any client can declare it through the ordinary generated protocol; React is an authoring adapter. Controls reference compact shared theme tables rather than copying them. Adding a skin requires neither a runtime build nor a generated-contract change; adding a runtime capability still does. The contract exports neutral field/part vocabulary and encoders, not concrete looks or design tokens.

An unskinned control paints no implicit background, label, indicator, focus decoration or transition. Authored layout and semantic actions remain available, including deliberately invisible hit regions. Explicit skin rows, control-owned paint or separately authored Canvas content enable only their declared presentation; absent decoration contributes no preset padding or chrome. Resolution ends at authored sources and the neutral defaults of an explicitly enabled primitive. Missing appearance or motion never selects a fallback skin.

Themes share part appearance, measurement and motion through ordinary components and assets. Per-control overrides take precedence; inherited fonts scale theme-relative dimensions. Native state resolution and AnimationSystem produce feedback on the Host clock, preserve continuity when interrupted and respect reduced motion. Resource replacement follows exact component lifetimes. The [presentation implementation](../../crates/ipp-core/src/world/systems/gui/presentation) and [motion implementation](../../crates/ipp-core/src/world/systems/gui/motion) own resolution rules and fields.

Parts may use shared Canvas paints with native state inputs. Decorative paint bounds never change hit geometry or clipping ownership. An anchored popup may share its background contour and paint coordinates with its touching anchor, including after native placement flips it; this forms one continuous optical surface while retaining ordinary overlay input and ordering. Layout owns the evaluated geometry and skins own its shading, without client-side geometry mirrors or a new renderer.

### Client skin ownership

Cybertron reproduces the former default appearance as an explicit client skin. Glass is a complete peer on the same interfaces, independent of core look tables or implicit Cybertron parts. Common authoring functions may be shared, but neither skin silently supplies missing definitions for the other. Callers select a skin or deliberately author their own parts; no compatibility shim reinstates the removed fallback.

The reusable GUI kit requires an explicit skin definition/provider and separates component composition from skin recipes. Dropdown triggers and their open lists form one continuous surface in every skin; placement and input remain native overlay behavior. React native declarations resolve their appearance role from the nearest explicit provider in the same World; explicit control skins take precedence and controls may opt out of inheritance. Themes have stable World-local identities. Switching changes appearance bindings and authored layout metrics while preserving controls, committed values, editing, selection, focus and scroll position; native interaction follows the resulting layout. Prepare assets before switching visible bindings. Failed loading leaves the prior ready skin selected and reports through existing diagnostics/application handling. Native states and AnimationSystem drive feedback without per-frame client callbacks, copied control state or per-control theme expansion; analytic shapes, shared shader parameters, retained batches, clipping and asset recovery remain the rendering path.

The same client provider may supply optional Plot paints, materials and frame defaults under the [chart material contract](rendering.md#authored-paints-for-chart-data-marks); explicit chart appearance takes precedence and native geometry/data ownership is unchanged.

Applications own skin preferences and persistence, apply saved choices before visible GUI mounts, and may use different skins in different scopes or canvas Worlds. Core stores neither application skin names nor a selected-skin registry. The shared demo application switches Cybertron and Glass without remounting control subtrees.

Explicit setup and direct contract/caller migration buy independent skin delivery and predictable styling. The [runtime strategy](../plans/runtime-and-rendering.md#gui-implementation-approach) and [React strategy](../plans/react-reconciler.md#gui-declarations) cover real rendering and switching evidence.

## Client-managed content

A client-managed input target is an ordinary GUI control whose application behavior lives in a client. Core retains focus, capture, eligibility, spatial routing and exact target/session lifetime validation. Ordered typed keyboard, committed text, pointer and wheel events reach the client through the standard protocol. Authored key-consumption policy can retain Tab and Escape while preserving an explicit focus escape. Platform adapters keep clipboard and IME ownership. Observation and input delivery do not grant a client control of Host clocks or evaluation.

A terminal uses this boundary: a client owns a pinned headless Ghostty instance as the authority for screen, scrollback, cursor, modes and terminal input encoding, and authors compact Canvas glyph runs, backgrounds and cursor paint through ordinary ordered batches. World components hold presentation, not another emulator. RenderService retains font, clipping, colour, depth, Surface and GPU ownership. Ghostty's Unicode state does not expand IPP's text rendering guarantees. Host clocks and AnimationSystem own presentation animation.

The browser terminal client runs Ghostty and a BashKit shell in one dedicated Worker, independently of the IPP Host Worker. Their byte-oriented APIs connect locally; every IPP-facing interaction, including resize observations and cockpit commands, uses the matching generated client and standard protocol. The existing [worker connection API](../../packages/ipp-client/src/worker.ts) and [MessagePort transport](../../packages/ipp-client/src/transport.ts) transfer owned buffers without requiring shared memory. Any future transport must preserve the same interface, wire messages, ordering, backpressure and lifetime semantics, selected at connection creation without changing terminal code. A shell runtime's own hosting requirements remain independent.

Applications explicitly start terminal sessions and own shell cleanup plus removal of their authored content. Loading presentation never launches a shell. Client input bindings invalidate with their session or target; late input and display writes cannot cross replacement lifetimes. Bounded shell I/O preserves bytes and terminal replies under backpressure. Persistence can retain authored presentation but cannot resume an emulator, shell or live input binding. The tradeoff is protocol traffic and explicit client lifecycle in exchange for independently scheduled terminal execution and reusable input capabilities without a core terminal dependency.

## Client and persistence boundaries

### Correlated wheel hit

The physical input result identifies the eligible GUI control under a wheel event, including its exact lifetime and presentation path, independently of whether that control or a scroll ancestor consumed the delta. Native routing resolves this once against the same view and blockers used for dispatch; applications can use the existing unconsumed delta to operate panel-level gestures without stale hover state or copied hit geometry. This extends the input result across native and browser transports, while leaving picking, control priority and keyboard focus in the existing input owner.

### Controlled React kit values

Complete React kit controls interpret a supplied value or checked prop as application-owned intent. Native input still commits immediately to the ordinary runtime field; after reporting the change and allowing the React update to commit, the adapter reconciles the latest supplied prop against the latest observed native value. An unchanged prop therefore restores a rejected edit through locally lifetime-fenced handles and compare-and-set writes. This is asynchronous convergence, not a promise that a remote control cannot briefly display a native edit. Delayed observations and superseded writes must not overwrite newer interaction, and range changes must preserve native constraints.

Default-value props initialize uncontrolled controls once. Public change callbacks omit subscription seeds and the adapter's own write echoes; observation hooks remain available for initial values and changes from any writer. Low-level component declarations keep their changed-prop-only authoring contract, and root unmount, omission and symbolic identity semantics do not change. This gives kit forms application-owned intent while preserving one authoritative runtime store and native editing/IME.

The optional `@ipp/react/gui` entry point produces ordinary entity/component declarations; browser composition stays in `@ipp/react/web`. Reusable composites, such as tabs, trees, dropdowns, menus, popovers, tooltips, dialogs, toasts, steppers, colour pickers and progress or status displays, live in the `@ipp/react/gui-kit` entry point beside it, built only from those declarations and independent of examples and tests; they observe the fields the runtime writes and keep only application data of their own. Keys retain entities, refs resolve after acknowledgement, and render-time work has no transport side effects. Momentary-effect callbacks capture and bubble along the logical ancestor path pinned to their effect, including delayed delivery; value callbacks follow field subscriptions and bubble through React's own element tree. Callback-only changes issue no structural writes. JavaScript propagation controls only callbacks; native browser default policies must also be chosen before asynchronous runtime responses. [React composition](authoring.md#react-host-composition) owns declaration scopes and attached-World cleanup.

Clients read controls through ordinary component reads and field subscriptions, and focus, pointer interaction and active items through GUI System queries. A client's semantic action is a `GuiAction` batch command naming the control's entity, component and incarnation; it applies at its operation's mutation boundary like any command, and the batch outcome is its only result. It is refused without effect, stopping the batch, when the target lifetime no longer matches (`StaleTarget`), the stored eligibility fields exclude it (`Unavailable`), the action does not fit the control role (`UnsupportedAction`) or the resulting value breaks the field's constraints (`InvalidValue`). Value actions are ordinary field writes observed through field subscriptions. Press, submit and focus changes publish momentary effects at that boundary, in ingress order, with the tick of the frame applying the batch. Logical focus set by a command has no owning input session: any client may blur it and closing a session keeps it. A semantic button press is momentary and moves no focus; in a selecting group it also selects its item. Routed physical input keeps its delivery tickets.

These reads, subscriptions and actions are the machine-client contract: autonomous agents and other programmatic clients observe and actuate GUI through them. Entity/part identity and invalidation before reuse survive visual-only change, so a reskin or relayout never retargets a handle; compare-and-set gives conflict-instead-of-overwrite where a client needs it. Record layouts follow the pre-stabilization policy and clients regenerate against their runtime. Platform accessibility adapters remain separate work; machine operability does not imply screen-reader support.

Component fields, including control values, follow existing [snapshot ownership](protocol-and-schema.md#snapshots-and-world-replacement). Focus, capture, text selection, provisional composition, active items, recorded invokers, pending delays and repeats, pending input/actions and GUI interaction playback, including skin transitions, are System state and are not saved; the presentation preferences are saved like other World-level System state. Restored Worlds reconstruct GUI output and use fresh runtime handles.
