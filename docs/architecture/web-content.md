# Web Content on Canvas

[Architecture overview](../architecture.md) · [Rendering](rendering.md#surface-presentation) · [Implementation strategy](../plans/runtime-and-rendering.md#web-content-producers)

## Ownership and sources

CanvasHtml is an ordinary headless Canvas leaf. Its component owns its authored source reference and logical size once; evaluated placement, clipping, layers and Surface mapping follow ordinary Canvas publication. DOM nodes, browser instances, platform handles, pixels and graphics contexts never become component or protocol state. CanvasHtml does not introduce another renderer or an implicit World attachment.

A Host-owned WebContentService owns source resolution, producer requests and lifecycle. Native CEF renders browser pages; browser HTML-in-Canvas captures eligible same-origin DOM content. These are distinct source capabilities, reported explicitly, rather than a promise that a browser can capture arbitrary cross-origin pages. Browser source registration retains the DOM object in its owning adapter and exposes only a scoped name to the runtime; its resolved registration lifetime fences pending work. ElementImage capture and import share the associated canvas authority: a separate staging canvas cannot directly supply another canvas context's images. Any bridge to a different renderer canvas must independently establish accelerated transfer and correct content. Canvas replacement requires explicit rebinding. Source withdrawal or replacement cannot silently retarget an existing request. Navigation and browser chrome remain client concerns. Browser DOM content can bind to an exact client-managed GUI input target: core routes pointer and wheel coordinates through the Surface, while the platform adapter grants native DOM editing only while that target holds focus. The client owns navigation and DOM form state; no DOM object or browser history enters World components. Temporary DOM hit-test geometry must not install a flat input overlay over curved content. DOM paint changes publish fresh immutable images through the same fenced capture boundary.

Host clocks and event loops drive browser work, including CEF's message pump and external BeginFrame. Platform callbacks may perform the scoped GPU import needed to own a frame and enqueue its completion; they never mutate or reenter a World. The renderer owns allocation, color normalization, publication image residency and retirement through the existing device boundary. No producer may fall back to CPU pixels, screencasts or CEF OnPaint; missing capabilities produce an explicit unavailable result for the affected leaf.

Browser acceleration is a capability of the established Host environment, not a consequence of HTML-in-Canvas API presence or a hardware WebGL context. A producer path whose implementation may fall back to internal CPU readback is available only when the Host can establish its accelerated preconditions. Otherwise it reports unavailable. A controlled browser harness can prove those preconditions for its launched environment; that evidence does not guarantee them in an ordinary web page. An enforceable production observation for the transferable-image bridge remains an open integration gate.

## Completed images and frozen output

A completed World publication selects an immutable web image version. A producer completion is admitted at the ordinary service/World boundary and dirties only its dependent Canvas output; it is not a component-value revision or an authored field write. Until adoption, newer full frames may replace a pending frame. Once selected by a publication or submitted draw, that image's pixels remain unchanged until all consumers release it.

A frozen branch therefore keeps its last completed web image while current parent placement still applies. Producer activity cannot animate a frozen publication or make its completion evidence claim newer pixels. Surface cache dependency stamps include the exact image version and residency, so a web repaint invalidates content caches even when authored components and geometry do not change. Existing optional refresh policy still decides when eligible caches repaint; completion observations retain the image provenance actually presented.

Each request and completion is fenced to the Host, exact World, entity and component lifetime, resolved source registration, current producer request and renderer context. Source changes, resize, teardown and replacement reject stale delivery before adoption. Request identities describe asynchronous work, not revisions of stored component values. Publication retention is subordinate to mandatory lifecycle invalidation before reuse.

## GPU lifetime and recovery

Borrowed producer storage must become renderer-owned storage before the producer's ownership window ends. CEF's pooled DMA-BUF cannot escape its callback: the renderer copies it and completes every GPU read of that borrowed storage before returning. Submitting a fence does not extend CEF's lifetime. Browser transfer snapshots are closed or released after consumption or rejection under their actual platform lifetime contract. Platform adapters keep import details outside the common headless interface.

Context loss invalidates residency without inventing replayable pixels. Producer snapshots need not be retained for recovery after their GPU import completes. An active World requests a fresh frame and adopts a new image version through normal publication. If a platform retains an exact snapshot for another reason, it may restore the same image version only when it reproduces that image exactly. A frozen GPU-only image remains unavailable after loss until a new valid publication can replace it; a newer page image must never impersonate its old version. Other content and usable headless state continue. Efficient normal rendering takes priority over seamless recovery; recovery never requires a CPU copy or retained duplicate of every producer image.

Count and byte bounds cover published images, pending completions, import staging and GPU retirement together. Admission reserves capacity before import; exhaustion drops or rejects the new frame explicitly while preserving still-valid published content. Coalescing cannot release storage still used by an outstanding platform operation or GPU draw. Limits and allocation algorithms belong with the implementation.

## Native engine distribution

CEF is an on-demand platform dependency of the native GLES Host distribution, loaded from one exact verified installation. Common source/component schemas and an explicit unavailable provider compile for headless and WASM Hosts; neither a capability Cargo feature nor a CEF-enabled distribution axis is added. The [workspace policy](rust-workspace.md) continues to govern dependency ownership and measured artifact costs. Deployments supplying the native engine include its pinned runtime and platform requirements; missing installation is an explicit capability failure, never an implicit download at runtime.

Development tooling shares immutable verified browser/CEF installations across source worktrees and publishes an installation atomically under a cross-process lock. Versions coexist; mutable Cargo targets, browser profiles, evidence and process ownership remain separate. Ordinary worktree/build cleanup never removes the shared installation. The browser suite pins the verified latest stable Chrome with HTML-in-Canvas enabled; a version bump is a deliberate tested dependency update.
