# React GUI stress benchmark

The stress benchmark measures one GUI-enabled build at one source revision through a fixed React workload on real browser/WebGL or native/GLES paths, with separate timing, capture, work and allocation windows. Native timing uses the explicit ordinary release GLES Host under `target/performance-build/gui-native`; its executable and target contract hashes must match `build-identity.json` before launch. Both browser and native timing compare the recorded build source hash against all current tracked and unignored source bytes, including dirty files; stale artifacts require rebuilding. The separate `--instrumented` native mode selects `gui-native-instrumented`, labels diagnostic output explicitly and disables ordinary latency samples. Run `python tools/ipp.py benchmark native --scene gui-stress --egl-dir /usr/lib64 --instrumented --software --repetitions 1 --samples 1` for a separate release diagnostic capture with software Chromium; native GLES device identity remains independently reported. Ordinary timing commands reject `--software`.

Run `ipp-browser-env python tools/ipp.py benchmark browser --scene gui-stress --repetitions 3` for the worker/WASM/WebGL path, or `ipp-browser-env python tools/ipp.py benchmark native --scene gui-stress --egl-dir /lib64 --repetitions 3` for the native GLES host and generated WebSocket client. Correctness runs through `python tools/ipp.py regression --only test:gui-stress:browser` and `IPP_EGL_LIBRARY_DIR=/lib64 python tools/ipp.py regression --only test:gui-stress:native`; `python tools/ipp.py test gui-stress` runs one repeat as the maintained correctness suite. Its strict build includes the actual stress scene and drivers without compiling unrelated examples.

## Workload

The [workload](../../examples/gui-stress/workload.ts) fixes seed, viewport/DPR, orthographic camera, assets, warmup, action order and independent panel-count and per-panel-tree-size sweeps: 1/4/9/16 panels at 16 explicit rows and 4 panels at 8/32/64/128 rows. Each logical panel contains layout, text, button, checkbox, slider, text input, image, drawing, scrollable explicit rows and a 10,000-item VirtualList; a separate cached raw Surface contributes drawing and text. Each repeat mounts a fresh React root and entities, resets the camera, verifies the initial list anchor/range, warms the scene, then runs six cycles of idle, one-subtree text edit, layout, theme, callback-only, semantic button press, checkbox toggle, routed physical slider drag, virtual scroll, camera-only update, animation seek, cache-idle and keyed churn. The legal virtual-scroll targets stay distinct even at the optional 32-cycle maximum. The harness verifies logical panel and raw-Surface counts, semantic roles, observed effects, callback revision, control mutation, fresh list ranges, raw drawing regions and meaningful changed pixels. Skipped actions fail rather than reducing the workload.

After each acknowledged action, `frame(view, { afterOutputs })` requests Host-admission evaluation cuts for the exact root and child outputs and waits for a completed draw containing them. This measures post-admission draw completion including the barrier, not the first instant an action became visible. Correctness runs do not collect latency samples; those fields remain `null`, not zero. Capture publication/sequence identities remain distinct from World ticks. GUI traffic counts logical batches (one per client `batch()` call), the pages they occupy under the contract's page limits, and ordinary mutation operations in panel Worlds, while idle/callback-only zero-write and local-subtree bounds remain asserted. React writes one `SetField` per changed field, so the one-subtree text edit is one batch to the first panel's World with at most seven operations: the title text and the three color channels of the previously and newly highlighted row indicators. A toggle settles with the value it applied and is observed as the `checked` field; it publishes no effect. Whole-Host/all-child work diagnostics are required.

The Host collector samples ordinary layout after each actual Host evaluation, independently of presentation. Per-World samples identify exact incarnations, ticks and evaluated/unavailable status; unselected layout and unavailable totals remain explicit. Host totals include unpresented Worlds and retained totals of retired lifetimes, without recounting cumulative work of unevaluated Worlds. No component mirror or protocol publication is added. Correctness runs include a separate untimed probe for unpresented layout, retirement and missing capability on both graphics backends, outside the workload and its timing windows.

After each sweep's timed work and captures, the harness records the list's anchor fields and independently inspects direct-child `GuiVirtualItem` indices. A subsequent `afterOutputs` draw must include a later evaluation of that Canvas; reinspection must retain the same item identities/indices, and the control anchor must remain unchanged. The report retains exact World/list identity, item indices, inspection/inclusion/verification ticks and draw sequence. Bounds come from those observed declarations accepted by ordinary indexed layout, never from the requested/wanted range. Empty, discontinuous, missing or changing observations fail; the observation fence and inspection work stay outside timing/capture-work windows.

## Report

`gui-stress-report.json` identifies source revision/diff, workload hash, target contract/runtime/asset hashes, backend, machine, browser and graphics device. Each sweep retains initial/final completed-frame PNGs and per-action distributions of in-page update-to-acknowledgement and update-to-completed-frame latencies. Timed steps call `presentation.frame()` after each acknowledged action using the causal output cuts described above; no PNG encoding, `readPixels` or per-frame capture enters those windows. Correctness/statistics captures run before and after them. The semantic control-press latency includes action, press callback and frame; it is separately labelled and must not be mixed with authoring-update latency. Timings include React, generated client, transport and runtime scheduling; they are neither isolated renderer CPU nor FPS. Keyed churn alternates remove and re-insert epochs, so its samples describe two populations.

A separate warm local-edit/callback-only probe reports layout, text and retained rebuild deltas. The ordinary browser build records a separate Chromium worker sampled-JS-heap allocation window, which is **not** a Rust/WASM allocator measurement. Timing runs use the normal `render` build. A separate `render-instrumentation` environment captures mixed actions and warmed 24-idle-frame windows for each panel-count sweep through the same live generated Host profiling reader as native. `core-profile.json` retains semantic per-World/System/phase CPU and allocation records; no slot-position interpretation is required across different selected-System schedules. Native `--instrumented` captures a separate action window through the live generated Host profiling reader; `native-cpu-allocations.json` retains semantic System/phase and fixed stage records with exact Host/World/incarnation/composition identities, nanosecond CPU durations and allocation/reallocation call and requested-byte totals. Exclusive allocation categories must sum to captured-thread totals; inclusive stage durations must not be summed as wall time. The evaluation-thread scope explicitly excludes background allocations and does not establish retained memory. The artifact is read after stopping, then released; ordinary Hosts explicitly report instrumentation unavailable. Native GPU-resident bytes remain in frame diagnostics. Missing diagnostic groups are unavailable, never zero. The narrow maintained [profile capture tests](../profiling/gui-profile-capture.test.ts) reuse this real fixture and environment drivers to verify rendered before/after frames, same and distinct System compositions, retired/recreated World identities, capture readback/release and exact captured-thread category totals. Full capture arrays live in separate JSON artifacts; event logs retain IDs and summary counts.

The report's `memory` section samples optional external providers after timing, work and allocation windows. IPP-accounted GUI, glyph and Surface-cache byte counters remain distinct from [Linux DRM fdinfo](https://docs.kernel.org/gpu/drm-usage-stats.html) client memory and [Chrome MemoryInfra](https://chromedevtools.github.io/devtools-protocol/tot/Tracing/) process backing allocations. Each observation names source, scope, byte units, sample time, capture/run identity and device/process/client identity where available; byte values are decimal strings to preserve exact integers, and unavailable observations carry a reason rather than zero. Duplicate descriptors for one DRM client are counted once; shared buffers can still overlap across clients. Chrome allocator parents and children remain separate and must not be summed. Neither Chrome backing sizes nor IPP-accounted bytes establish physical VRAM residency. In native mode, Chrome observes the presentation client browser; DRM samples the owned native Host. `gpu-memory-raw.json` retains memory-dump events and DRM fields, while `memory-frame.json` and its PNG identify the completed frame around the observation. A missing requested dump, inaccessible descriptor or unsupported provider remains explicit. A dedicated trace is stopped only after this adapter successfully starts it; an already active trace is left with its owner. No external sample enters latency distributions, and no subtraction between providers establishes a leak.

`benchmark` selects hardware ANGLE (`--hardware vulkan` by default, or `gl-egl`), records it in the pipeline's `summary.json` and rejects software renderers; still verify the report's unmasked device identity before describing browser measurements as hardware. Native GLES also requires the reported EGL/device identity. Preserve the pipeline evidence directory, logs and exit status with each report. Capture and allocation/profiling windows must remain separate from timings when extending this benchmark. When comparing reports from different revisions, run them on the same machine, profile, assets, viewport, DPR and warmup.

## Counted panels and revision comparison

Supplemental React panels contain exactly 51, 136 and 1001 observed entities in their Canvas Worlds, without control skin expansion or virtual items. The real transport reports declaration-to-completed-frame time, inspection time and encoded inspection JSON bytes; local colour and position edits retain acknowledgement/completed-frame distributions. Completed before/after captures verify visible paint and changed pixels. These primitive panels supplement the rich stress scene's semantic controls and routed physical slider drag; they are not replicas of the retired node API.

`benchmark native --scene gui-stress --egl-dir /usr/lib64 --compare-checkout <existing-checkout> --pairs 1` alternates A/B/B/A ordinary timing runs. Prepare the second checkout's matching GUI artifacts and ordinary release Host first; the runner preserves its source contents and does not reset, commit or create checkouts. `--reuse-build` also requires the primary products to be prepared. Repeat blocks with `--pairs 1..4`; `--samples` and `--repetitions` retain their workload meaning. Browser comparison uses the corresponding browser command and prepared render distribution. Each run keeps its own report and captures; `gui-paired-report.json` records build/source/fixture identities, per-run distributions and B-minus-A differences. Workload, fixed fixture-source manifest, assets, contract, settings, machine, renderer, browser and compositor must match. Runtime binaries, emitted client JavaScript and bundled React implementation are the code under test and may differ; their actual artifact hashes remain recorded. The fixture-source manifest covers the stress scene, workload, diagnostic panel and fixture driver with its camera, System-selection and GUI-action helpers. The common Node orchestration harness is identified separately. The report retains actual Chromium launch arguments, requested ANGLE/GPU-compositing settings and native renderer observations. Repaint/reuse frames normalize to the same cached presentation while dimensions, bands and fallback modes remain distinct. Machine load averages expose external contention without claiming it belongs to IPP. Thermal observations are explicitly unavailable unless `IPP_GUI_THERMAL_NOTE` supplies a manual observation; no sensor readings are inferred. Use serialized, verified hardware for performance conclusions; software runs validate harness behavior without timing thresholds.
