# Retained Surface rendering measurements

Run `python tools/ipp.py benchmark browser --scene retained-gui --frames 60`. For this scene `--frames` counts streaming screen updates; Blender stress options such as `--preset`, `--group` or `--instrumented` are rejected. The opt-in workload runs the same maintained scenario as `python tools/ipp.py test retained-gui` with a longer streaming interval. It builds analytic Surface and GUI-enabled worker runtimes and drives both through generated clients, immutable font/drawing assets and actual WebGL. Results and completed-frame images go to `target/performance/retained-gui/`.

## Scenario

The terminal fixture presents the application's printable ASCII glyph set as positioned rows. Its generator accepts visible row/column counts, typing, cursor blink, scrolling, full replacement and an `unseen` mode that slides a window through Latin-1, box-drawing and icon glyphs never shown before. The scenario:

- counts cold misses and populations from counters accumulated over every rendered tick, then settles to a warm frame without uploads or rebuilds;
- derives the glyph record size from a full-screen replacement and bounds typing to one row and cursor blink to one shape record;
- reuses local geometry for oblique and mirrored rear views of the same panel;
- shares font coverage across three panels, restores the graphics context, retires geometry for smaller screens and releases everything when cleared;
- grows the atlas past one page with unseen glyphs at a larger band, keeps it within the page budget while sliding through more glyphs than the budget retains, and proves eviction when the first window populates again;
- renders a GUI panel mixing a gradient shape with glow, atlas glyphs and a curve drawing, captures its mirrored rear view, and compares sparse and filled controls under one camera, viewport and DPR.

Glyph population is bounded per frame by time rather than a fixed count. Each frame populates at least 32 missing entries, then as many as a 2 ms budget covers at the estimated per-glyph cost, up to 512 (`GlyphPopulationBudget` in [the glyph atlas](../../crates/ipp-render-gl/src/services/render/retained/glyph_atlas.rs)). Native renderers refine the estimate from measured population passes; WebGL keeps a fixed estimate because its draws execute in the GPU process. Cold text within the budget therefore samples the atlas from its first frame instead of showing analytic glyphs over several frames. The cold counters are totals the runtime accumulates over every rendered tick and reports in each capture's `statistics`, so they do not depend on how population splits across frames.

Before the atlas phase the scenario lowers the renderer-owned glyph atlas budget through the testing override (`setGlyphAtlasLimits` from `@ipp/client/testing`) (both variants also simulate context loss, so they run the `instrumentation` build) and disables idle expiry, so eviction does not depend on the device-derived default. Pages retired while the windows slide are therefore pressure evictions: the scenario keeps every step within the configured budget and requires a positive accumulated `glyphPageRetirements` count. Pages still release when no World demands any glyph, so the cleared frame holds no atlas bytes.

Analytic builds lack the retained counters and report them unavailable, never as zero. The GUI counter `guiResidentBytes` is the per-Surface GPU storage holding retained shape and glyph batches, including the room each slot reserves to grow; `glyphResidentBytes` counts atlas pages separately, at one byte per texel of single-channel coverage. Shapes and glyph quads keep the separate instanced record layouts defined in [the retained records](../../crates/ipp-render-gl/src/services/render/retained/records.rs).

## Expected upload sizes

Each glyph is one instanced `GuiGlyphRecord` of 64 bytes (the size is asserted beside the type): its quad, atlas rectangle, tint and clip. The benchmark terminal shows 12 rows of 36 columns, one retained text piece per row, so every scroll or full replacement retexts all 432 glyphs in place: 432 records, 27,648 bytes. Typing retexts one row, 36 records or 2,304 bytes, and cursor blink uploads at most one 192-byte shape record. A warm frame uploads nothing. Runs that drew glyphs and boxes as one triangle list of shared 184-byte vertices, six per quad, uploaded 476,928 bytes per full replacement and 39,744 per typed row, and runs before that with 152-byte vertices 393,984 bytes; runs before the unified GUI program drew glyphs from 32-byte vertices, 82,944 bytes. The record counts per update match those runs' quad counts: only the bytes per quad changed. `terminal_updates_upload_exactly_the_changed_rows_glyph_records` in [the batch tests](../../crates/ipp-render-gl/src/services/render/retained/shape_batches_tests.rs) pins these sizes, and the scenario derives the glyph record size from each run's full replacement, so a change to the layout or the rebuild scope shows in both.

## Whole-Surface cache mode

`python tools/ipp.py benchmark browser --scene retained-gui --frames 60 --surface-cache` runs the same scenario with every terminal workload panel opted into whole-Surface caching and writes to `target/performance/retained-gui-surface-cache/` unless `--output` is given. The policy (`BENCHMARK_SURFACE_CACHE_POLICY` in [the scenario](../gui/retained/scenarios/retained-gui.ts)) caches at every distance at the terminal view's screen density and uses the highest refresh cap, so each streamed update presents at its next frame while unchanged frames reuse the image. GUI control panels stay direct. Distance bands, refresh caps, interaction priority and lifecycle are asserted by the `surface-cache` suite rather than measured here.

`comparison.json` then adds `surfaceCache`: per build, the policy, the seven per-frame cache counters of the warm frame (`surfaceCacheRepaints`, `surfaceCacheReuses`, `surfaceCacheDirect`, `surfaceCacheFallbacks`, `surfaceCacheAllocations`, `surfaceCacheEntries`, `surfaceCacheResidentBytes`), the running totals after the last streamed update and the warm frame's cache records. Compare it with a run without the flag under the same machine, viewport and streaming count; a run whose renderer does not yet cache reports empty records and zero counters.

## Reports

`comparison.json` identifies its run: source revision with a hash of uncommitted changes, machine and Node identity, the pipeline run directory when started through `tools/ipp.py`, the process arrangement (browser worker, or native GLES for `check:gles-retained-gui`), the streaming count, DPR, viewports and workload dimensions. Each build entry names its runtime features, evidence directory, browser version and device identity strings, and `softwareRenderer` marks devices that rasterize on the CPU (SwiftShader, llvmpipe). Every label both builds capture has `comparisons/<label>-expected.png` (analytic), `-actual.png` (retained) and `-diff.png`, with the changed-pixel fraction, text-mask agreement and coverage ratio checked against the tolerances recorded beside them. Each build's evidence directory also holds its per-label captures and `workload.json`.

Each streamed-update sample records two latencies from the same update. `elapsedMs` is Node-side wall time from requesting the React update to having the next completed frame, so it also contains the harness round trips to the page, base64 pixel transfer and PNG writing. `inPage.updateToReadbackMs` is measured inside the page from starting the update until the next completed frame's pixels arrive there; it splits into `updateMs` (until the runtime acknowledges the update) and `captureMs` (requesting the next completed frame until its pixels arrive), and `readbackMs` is the worker's wait to finish GPU work and read the pixels back. The in-page interval therefore spans the frame that applies the update and the frame that presents it. `comparison.json` summarises each measure's median and 90th percentile per build under `timings`, with the definitions beside them in `timingDefinitions`; per-sample values stay in each build's `samples`.

These timings still include client, transport, scheduling and readback and must not be reported as isolated rendering cost or FPS; `timingScope` in `comparison.json` repeats this. Software GL proves correctness in its environment, not mobile performance.

## iPhone 14 Pro procedure

Physical-device measurements are pending a device; no iPhone result is implied by the automated browser suite. Use the maintained gallery on the device to compare the Aurora, Ember and Neon materials. Controls use retained shapes and Nerd Font icons; the waveform, reference grid and pulse remain Surface curve drawings:

Use a physical iPhone and a Mac with Safari. Enable Web Inspector in the iPhone's Safari advanced settings, connect by cable, trust the Mac when prompted, and select the device's gallery tab in Safari's Develop menu. Network inspection can be enabled after the initial cable connection. Apple's [device inspection instructions](https://developer.apple.com/documentation/safari-developer-tools/inspecting-ios) own current platform setup; a simulator is useful for setup checks but does not supply physical-device performance evidence.

1. Build the standalone gallery with `python tools/ipp.py build gallery-site`, then serve it with `python -m http.server 8000 --bind 0.0.0.0 --directory target/gallery-site`. On the same network, open `http://<development-machine-address>:8000/` in Safari and select the GUI world. Use a trusted HTTPS endpoint when exercising platform features that require a secure context. Stop the server with Ctrl-C after the run.
2. Record the source revision and uncommitted diff identity, runtime build identity, iOS/Safari version, display orientation, viewport/DPR, presentation-quality settings used (including whether **Isolate GUI panel only** is active), power mode and thermal state. Keep these fixed between samples. Disable Low Power Mode and allow the device to cool between runs.
3. Confirm that the gallery's assets and controls have rendered, retain an initial image, then allow 10 seconds of warmup. Measure 30 seconds with Safari's remote Web Inspector Timelines recording while the panel faces the camera. Repeat with an oblique panel at the same projected size. Keep camera positions, animation and control state identical between skin samples. A missing resource or incomplete scene invalidates the sample rather than becoming a faster result.
4. Repeat while dragging the slider, scrolling, typing in the text field and blinking the caret. Record frame cadence distributions and long frames from the timeline, plus the exact recording interval and instrumentation. Save screenshots of idle, hovered/pressed where available, focused and disabled controls, and resize/orientation changes. Do not infer keyboard/IME acceptance from rendering measurements.
5. Repeat each sample three times and export each complete recording from the Timelines tab, retaining screenshots and device details beside it. Record which timeline categories were enabled; CPU, memory and screenshot capture add different observation costs, so keep a separate ordinary interaction sample with the inspector recording stopped. WebKit's [Timelines reference](https://webkit.org/web-inspector/timelines-tab/) describes recording and export. Report thermal drift and unavailable measurements explicitly. The automated terminal capture timings and interactive Safari cadence measure different intervals and should remain separate.

This procedure does not measure whole-Surface texture caching or cache transitions; see [optional Surface texture caching](../../docs/architecture/rendering.md#optional-surface-texture-caching) and the cache mode above for the automated comparison.

Safari timeline activity and process memory do not establish GPU command duration or physical VRAM residency. Record unsupported timer-query or memory providers as unavailable. Xcode's [GPU capture procedure](https://developer.apple.com/documentation/xcode/capturing-a-metal-workload-in-xcode) configures and runs an app target; it is not evidence that an arbitrary shipping Safari GPU process can be captured. A future app-specific investigation must identify its target and capture method separately, without claiming an existing IPP iOS Host.

## Low-end GLES device procedure

Use a physical Linux device with an actual supported native IPP build and GLES 3 implementation. This procedure does not add an Android or iOS Host. Record the device model, CPU/GPU, OS/kernel, EGL/GLES driver identity and library directory, available memory, power mode, temperature or thermal-throttling observations, and other active workloads. Install the repository-pinned tools and matching source/asset inputs on that device; do not substitute a desktop GPU run or software renderer for the requested device.

1. Run `python tools/ipp.py doctor --for gui-stress --egl-dir <device-library-directory>` and preserve its output. The GUI runner also uses a browser client, so both its browser prerequisites and the native libraries must work. Missing prerequisites remain pending environment work.
2. Run `python tools/ipp.py regression --only test:gui-stress:native --software --egl-dir <device-library-directory>` for bounded correctness. Retain meaningful completed-frame images and state assertions. The software option applies to the browser participant; inspect the native Host's reported renderer independently.
3. Run the [native GUI benchmark](gui-stress.md) on the device with the same EGL directory, fixed workload and three repetitions, one measurement process at a time. Verify the ordinary release Host identity and hardware renderer in the report before treating latency as a device baseline. Keep instrumentation captures separate from ordinary timing and preserve every pipeline summary, report and failure artifact.
4. Repeat the same identified build after cooling, and alternate revisions on the same device for comparisons. Record load and thermal changes beside the samples; do not claim comparability when workload, power settings, viewport, driver or compositor differs. Capture the same observable scene work rather than lowering its content to obtain a passing number.
5. Preserve available GPU durations and scoped memory observations with their originating frame and provider identities. Missing queries, disjoint samples and inaccessible driver statistics remain explicit. Shared DRM-client memory and IPP-accounted resource bytes are distinct observations, not terms in a leak calculation. Stop owned Hosts, browsers and capture sessions on success or failure.

For native World/System phase diagnostics, use the separate gallery trace command in the [performance guide](../../docs/development/performance.md#interpret-diagnostics) with the same device library directory. Preserve its bounded event counts and clock-correlation metadata; it is a separate workload and observation window from the GUI benchmark.

The procedures above are documentation, not a record of physical execution. Beads task `ipp-2pv8.14` owns the pending iPhone and low-end-device evidence; ordinary desktop WebGL/GLES validation has its own identified reports.
