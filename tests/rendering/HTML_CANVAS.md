# HTML-in-Canvas browser producer

This maintained prototype establishes the browser's accelerated producer boundary before its integration with IPP's Host admission and Surface rendering. It uses real Chrome, main-thread DOM layout, a producer WebGL context and a separate worker WebGL context. It does not yet establish IPP World/component fences, generated-client transport or final Surface composition.

Same-origin DOM has a separate, narrower production path: the [client adapter](../../packages/ipp-client/src/html-content.ts) captures DOM owned by the actual presentation canvas and transfers its ElementImage directly to that canvas's OffscreenCanvas in the renderer worker. The [WASM Host adapter](../../crates/ipp-wasm/src/services/render/web_content.rs) reserves capture capacity and imports into immutable renderer storage before CanvasHtml publication. This path needs no separate canvas or ImageBitmap export, so the compositor-dependent ImageBitmap bridge below is not involved. DOM paint changes recapture into fresh immutable images. The browser adapter binds a client-managed GUI target for curved pointer/wheel routing and gives native DOM controls keyboard, clipboard and editing focus only while core authorizes that target. Chromium supplies DOM hit testing and caret positions; temporary query geometry is cleared before returning to the event loop. Nested accelerated canvas/video, cross-origin pages and browser/OS popup capture remain outside this path. Changing a page withdraws its registration and input binding; the browser pane keeps one stable GUI target across navigation. The `cockpit-browser` suite exercises links and history, input selection, clipboard paste, multiline text, numeric steps, checkboxes, radio buttons, a listbox, range input, scrolling and teardown at 2x display density through the real cockpit Surface, with completed-frame changes and disabled-flag instructions. OS-native IME and touch keyboard behavior still require device evidence.

ElementImage extents describe the DOM capture and can be scaled or fractional with browser/DOM zoom. Import rasterizes the complete capture at the explicitly admitted texture size; only fixed-pixel ImageBitmap imports require matching source dimensions. The `html-canvas:static` scenario covers display density and DOM zoom with actual alpha/orientation pixels, replacement, odd-sized resize, recovery and withdrawal. Import failures retain the underlying Host/device diagnostic for the caller.

Run the selected browser and installer checks through the pipeline:

```sh
python tools/ipp.py setup browser
python tools/ipp.py regression --suite html-canvas
```

The GPU scenario requires hardware WebGL and GPU compositing. The runner records Chrome's CDP GPU feature status before creating the producer, then validates the worker's hardware renderer before capture. A software run cannot establish this GPU path; `--only test:html-canvas:unavailable --software` exercises the absent-capability case alone. The shared Chrome pin, cache and flag selection live in [browser options](../../tools/build/browser-options.mjs) and the [installer](../../tools/pipeline/browser.py).

## Observed browser API

The verified stable build is Chrome for Testing 155.0.8059.84, revision 1697595, resolved from the [official stable feed](https://googlechromelabs.github.io/chrome-for-testing/last-known-good-versions-with-downloads.json). Its actual API still exposes `layoutSubtree`, `captureElementImage`, `requestPaint`, `ElementImage.width/height/close` and `texElementSubImage2D`. The [Chrome API-change article](https://developer.chrome.com/blog/html-in-canvas-ot-changes) describes `content="drawable"` for Chrome 155, but that attribute alone fails on this exact stable binary. The prototype targets the verified API directly and carries no older-version compatibility path. Reverify the API when advancing the latest-stable pin.

Interactive pages require both `chrome://flags/#canvas-draw-element` and `chrome://flags/#enable-experimental-web-platform-features`, followed by a Chrome relaunch. The first flag alone exposes `updateElementGeometry` but leaves the separately gated `ElementCanvasTransform` disabled: geometry updates are accepted without affecting DOM hit testing. The client capability check verifies an applied transform before offering HTML sources. The cockpit suite covers this incomplete configuration with real Chrome, requires setup instructions and both copyable flag addresses, and verifies that no interactive source is registered. With both flags enabled, it checks that clicking a different control does not activate a previously focused checkbox.

A captured `ElementImage` may only be drawn into its associated canvas, including that canvas's transferred OffscreenCanvas. Direct transfer to a worker preserves ordinary HTML/CSS but omitted nested accelerated canvas pixels in the verified build. Drawing the same capture in its associated main-thread WebGL context preserves those pixels. The producer therefore uploads the element into a reusable GPU texture, blits into its associated OffscreenCanvas, and transfers an immutable `ImageBitmap` to the worker. IPP's renderer can remain in the worker with a separate presentation canvas. Explicit upload dimensions avoid a resize-dependent default-scale mismatch; the blit also converts the framebuffer origin.

This is a browser-managed GPU-image bridge, with GPU copies; it is not a zero-copy claim. Chrome's [DrawingBuffer implementation](https://chromium.googlesource.com/chromium/src/+/refs/tags/155.0.8059.84/third_party/blink/renderer/platform/graphics/gpu/drawing_buffer.cc#728) exports an accelerated shared image when GPU compositing is active and explicitly reads back into an unaccelerated bitmap otherwise. Therefore a hardware WebGL renderer alone is insufficient evidence. Ordinary page JavaScript does not expose this compositor capability; production admission must use a supported Host environment and cannot silently assume every Chrome configuration provides acceleration. The prototype's harness refuses an unverified environment before capture.

## Ownership and evidence

The [producer](support/html-canvas-producer.ts) permits one in-flight bitmap and coalesces paints until acknowledgement. It closes the temporary ElementImage after copying and closes an unsent bitmap on failure. The receiving worker owns transferred bitmaps, rejects obsolete generations, and releases every consumed/rejected image. Its retained-image replay is an experiment, not a production recovery requirement: the accepted integration may discard GPU images after context loss and request fresh content.

The [scenario](scenarios/html-canvas.ts) and [browser driver](drivers/browser-html-canvas.ts) keep assertions separate from browser setup. Completed captures verify nested-canvas changes, straight-alpha/sRGB composition, orientation, resize, bounded coalescing, same-origin iframe content, excluded cross-origin iframe content, stale-frame release, exact retained-image replay after actual worker context loss with already-changed DOM, and disposal. Pixel readback exists only in this test's consumer capture. The delivery path never sends CPU pixels through JavaScript or WASM memory.

Each run saves environment identity, PNG captures and result statistics under `target/html-canvas-evidence/`. Reported latency measures capture-to-worker-import/draw-submission time. It does not measure physical display presentation or establish IPP end-to-end frame latency. The initial Linux AMD Vulkan measurements are environment-specific and are not a general performance guarantee.

## WebGL device adapter

The `html-canvas:device` scenario uses the same producer and image assertions with the real IPP [WebGL bridge](../../crates/ipp-render-gl/src/services/render/device/webgl/webgl.ts), ordinary bitmap shader and linear-to-sRGB root presentation. It establishes device import and drawing, not yet the Host request handshake, World publication or attachment graph.

`stageWebImage` takes ownership immediately and retains at most one bitmap of at most 64 MiB. The Host must reserve combined staging and destination capacity before capture or transfer; this local adapter bound does not replace that reservation. The renderer's `copy_web_image` consumes the exact stage once into an already allocated private SRGB8_ALPHA8 texture with matching dimensions. Import closes the bitmap even on failure or context loss, and restores the touched texture binding, unpack buffer and pixel-store state. Source orientation and alpha must already match the verified producer: [WebGL's unpack flags](https://registry.khronos.org/webgl/specs/latest/1.0/#PIXEL_STORAGE_PARAMETERS) do not reinterpret an ImageBitmap created with other semantics. Explicit release, bridge disposal and context loss close unconsumed stages. No recovery snapshot is retained.

Device completion fences flush submitted work and poll with a zero timeout. Nonreused names are owned by the creating device, deleted explicitly or on teardown, and invalidated across context restoration. The bridge bounds outstanding fence objects independently of renderer image accounting. The maintained device scenario exercises successful and mismatched imports, one-use and stale names, staging pressure, GL state restoration, real loss/restoration, disposal and eventual fence completion, alongside the completed HTML/nested-canvas images.
